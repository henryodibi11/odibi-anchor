# Odibi Anchor operating contract

Use Odibi Anchor for provider-neutral reliability and evidence. Users request outcomes; you own
orientation, implementation, and verification. Action help: `.assistant/references/odibi-anchor/`.

## ⛔ STOP — mandatory agent execution contract

**Odibi Anchor use is mandatory for every substantive repository, managed-project,
data, debugging, implementation, or multi-session task governed by these instructions.**
"Quick," "read-only," or "already known" never skips bootstrap, project verification, or
task registration. Complete the steps below in order before searching, editing, testing, or
querying data. If a step blocks, follow its structured next action or STOP; never rationalize
a bypass.

### 1. Bootstrap the named project in the same persistent Python process

Run the managed launcher; it needs only the project ID:

```python
import runpy
namespace = runpy.run_path(
    "<instruction-root>/.assistant/agent_bootstrap.py",
    init_globals={"ANCHOR_PROJECT_ID": "<project-id>"},
)
anchor = namespace["anchor"]
ROOT = namespace["ROOT"]
MANIFEST = namespace["MANIFEST"]
orientation = namespace["ORIENTATION"]
bootstrap = namespace["BOOTSTRAP"]
startup = namespace["STARTUP_PACKET"]
assert bootstrap["success"] is True
assert orientation["kind"] == "orientation"
assert startup["status"] == "ready"
```

Install only when missing or changing version (latest-stable pin), then restart once and
relaunch. Bootstrap once per process; new tasks use `new_session`. Run `setup_host` only
initially, after upgrades, or for diagnosed drift. Never guess a version, set `ANCHOR_HOME`,
or apply portfolio environment manually (host/creation notes: `workflow.md` "Contract details").

`"Use <project>"` never authorizes creation; if absent, STOP. Load `setting-up-odibi-anchor`
only for a missing portfolio, host ambiguity, recovery, explicit project creation,
an approved policy change such as retention, or another setup failure.
Never guess a portfolio mutation or edit its TOML directly.

The instruction root holds this file and `.assistant/`. If deterministic resolution fails,
follow doctor's next operation. NEVER use `exec`, `eval`, manual `sys.path` reconstruction, or a
standalone subprocess. Locating source or a failed init is not successful bootstrap.

ALWAYS assign every `anchor()` result and keep launcher results alive; after a restart,
re-bootstrap and start a fresh task. Use the launcher's process-bound callable, never
`from odibi_anchor import anchor`. Issue one Anchor call at a time.
Independent non-Anchor reads may run in parallel. Follow each prepared `next_operation`; use
`anchor("help", "action_name")` only when none covers the action; never guess parameters.
Before claiming success, read each result's `envelope` (`outcome`, `warnings`,
`effects.verified_readback`, `next_operation`); only `succeeded` is a clean success.
Prefer `startup["managed_artifact_actions"]` to filesystem traversal; report a missing action
before any bounded fallback.

### 2. Verify the managed project before using repository or data context

Inspect `startup` (requested ID, target, artifact root, binding source); only if project
detail is missing, run:

```python
project_state = anchor("project", "status", output_format="dict")
```

- A request for an existing managed project requires a matching active ID and target before
  substantive work; it permits binding a fresh runtime to that project, never creation,
  retargeting, migration, deletion, or substitution.
- The immutable RouteBinding is routing authority; `workspace/.active_project` MUST NOT infer,
  redirect, or validate a route. If the binding names another project, end that runtime,
  relaunch with the exact ID, rebind every result, and verify before a fresh task.
  `anchor("project", "use", ...)` must not redirect an already-bound runtime.
- If an expected project is missing, ambiguous, inaccessible, or mis-targeted, STOP; NEVER
  substitute another repository or the Anchor source checkout. Approved creation or
  retargeting performs only that mutation (workflow setup lifecycle), then re-bootstrap.
- Before planning or editing, read and follow every applicable instruction file from the
  selected target root through each target path (at least `.assistant_instructions.md`,
  `AGENTS.md`, `CLAUDE.md`; host-injected contents count).
  More-specific nested guidance governs its subtree without overriding system, user, task,
  managed-project, or trust-boundary authority. Skip unrelated subtrees; if required guidance
  is inaccessible, STOP.
- Read `PROJECT.md` and the relevant Problem, decision, work-item, and Spec records before
  planning. Do not start deferred work, silently broaden an accepted item, or fabricate
  work-item authority. Never replace a managed `PROJECT.md` wholesale (keep frontmatter `id`,
  `project_type`, `target_root`); use `repair-descriptor` or `move-target`.

Managed artifacts, evidence and durable session notebooks belong in `artifact_root`; product
source, tests and Git work belong in `target_root`. Never mix them; gates may persist evidence.
Relative `touched` paths use `target_root`; managed edits use the artifact contract's
`absolute_path`, never a guessed path. Discovery grants no authority. Registration, recovery,
notebook/compute rules: [`workflow.md`](.assistant/references/odibi-anchor/workflow.md).

### 3. Establish task authority before substantive work

Never repeat orientation or query memory pre-task. After routing is verified, every substantive
task MUST establish an inquiry; acceptance returns bounded memories:

```python
session = anchor("new_session", name="bounded_task_name", inline=True, output_format="dict")
task = anchor("task", "Investigate bounded work.", goal="Define scope, checks and destination.",
              mode="analysis",  # read-only
              acceptance_criteria=["Define completion checks."], output_format="dict")
```

Fresh source-capable and substantive artifact tasks need explicit project, trust, and
`workflow_id`: draft in a read-only task, close its obligations, bind a fresh producer, then
`accept_plan` before edits. Only `delivery_verified` completes a workflow; gates/tests grant
no delivery authority. Human approval binds the exact candidate and destination; high-risk
review needs a separate accepted read-only task (`reviewer_authentication=none`). Never
downgrade risk, invent authority, or synthesize evidence; only documented exceptions apply.
After a restart, call `anchor("task_rebind")` first; never reconstruct authority or absorb
changes into a new task (continuation: `workflow.md` "Contract details").
`scope` is one prose string. Use a truthful mode; never pick write capability to bypass policy.

For routine substantive tasks, immediately after task acceptance and before source edits, review
only the bounded, active-project/trust-scoped `memory_context`. Acknowledge selected memory IDs
and provenance, or report that no memories were selected. Do not scan the full store or treat a
candidate as authority or verification. Dispose every selection and record an evidence-backed
evaluation for each application; runtime blocks learning closure until every selection has a
disposition and every application is evaluated. If all pending selections are irrelevant, use
one `all_pending=True` disposition call, never a loop. If retrieval is unavailable, follow the
fail-closed/degraded policy without inventing evidence. Reject candidates via `anchor("reject",
id)`; withdraw/quarantine require promotion.

### 4. Read and apply every materially matched skill

Before a skill-owned action (matrix below or required-skill result), MUST load the skill via
the host or read `.assistant/skills/<name>/SKILL.md` and follow it; file presence is not
loading, and never claim an unread skill was applied. Only then register it:
`skill_result = anchor("skill_loaded", "<name>", output_format="dict")`. `reference_guidance`
is advisory, never a skill, gate, or runtime proof (`workflow.md` "Contract details").

### 5. Complete the exact delivery lifecycle for file changes

For every file-changing task (pass `output_format="dict"` to each call):

1. Inspect current source and preserve unrelated changes.
2. BEFORE editing any Python path, run
   `known_bad_result = anchor("known_bad", changed_files=["path.py"])`.
3. Make only the task-authorized edit, then immediately register every path with
   `touch_result = anchor("touched", "path")`.
4. After Python edits, run `preflight_result = anchor("preflight")` and
   `test_result = anchor("test")`. For other files, run the narrowest meaningful validation,
   never a ceremonial irrelevant test.
5. Review the complete final diff with `review_result = anchor("review")` plus judgment.
6. Run `gate_result = anchor("gate")`; nothing is deliverable until it succeeds.
7. Capture observations as encountered; at closure `assess` resolves obligations:
   `learning_result = anchor("learning", "assess", outcome="nothing_reusable_learned")`,
   or `capture` genuine observations and assess their IDs as `observations_recorded`. If gate is
   unavailable, assess, then `anchor("learning", "safe_stop", status="blocked", reason="...")`;
   it never passes gate.

Exact callable behavior may use the machine-verifiable memory lane. File cross-project
lessons in learning, project runs in managed evidence, defects in a Problem or Work Item.
Before closure, reconcile linked or touched Spec, Problem, Work Item, and `PROJECT.md`
statuses to verified outcomes only (both: `workflow.md` "Contract details"); re-read every
managed artifact you write.

Do not edit after a successful gate. For follow-up changes, first close that gate's
learning obligation, deliver to a clean authorized baseline (else STOP), then open a
fresh session/task and repeat the whole cycle. Checkpoint each feature boundary. Read-only
tasks owe no file, test, gate, or learning duties but need bootstrap, routing, and authority.

### 6. Obey blockers; never self-authorize

Branch, revision, target, project, process, or worktree changes can invalidate authority. On a
reported block, drift, missing task, stale routing, required skill, failed check, or learning
obligation, follow the stated recovery order. NEVER retry a failing action unchanged, edit
around a guard, disable enforcement, fabricate `obligations_paid`, count skipped tests as
passing, or claim completion from a summary. STOP when recovery needs approval, destructive
action, unavailable credentials, an unknown destination, or a choice between authorities.

### 7. Return a complete terminal contract

Every substantive project task's final response MUST use this contract:

```text
Terminal return required:
- Status: completed, blocked, or failed
- Exact project/repository, branch, and revision
- Outcome, files/artifacts changed, and statuses reconciled
- Checks actually executed and retained evidence
- Repository/host review, gate, and learning status where configured
- External/shared effects performed
- Commit, push, merge, deployment, and publication status
- Deviations, unavailable evidence, and residual uncertainty
- Decision or next authority required from me

Do not describe an unexecuted, skipped, unavailable, or failing check as passing.
```

Write `not performed`, `unavailable`, or `N/A` rather than omit a material field; re-read
persisted artifacts and external effects before claiming them. Stricter task-specific returns
extend this; casual conversation and simple factual answers are exempt.

Before substantive work, select and apply through the host every native skill whose
material intent matches the request; its `SKILL.md` remains the behavior authority.

Independent PR review uses universal guidance outside the native skill registry. Fallback
routing is explicit: when the host provides `reviewing-pull-requests`, apply that host
skill; otherwise load and follow
`.assistant/references/reviewing/independent-pr-review.md`. Never route independent review
to `cross-functional-pr`, and keep the native distribution aligned with the canonical registry.

Compose multiple skills only when each owns a material outcome, never for generic planning.
For a required direct skill, `anchor("skill_loaded", "<name>")` returns its
complete resolved content before registering it. Registration proves delivery,
not comprehension; verify application from the work and evidence.

## Operating principles

Reason from the outcome, scaled to risk; separate observation from interpretation. Reconfirm
destination and approval at each write, publish, deploy, delete, compute, or external-service
boundary (external targets: `workflow.md`). Ask only at real
intent, choice, or approval boundaries; keep one authoritative thread; handoffs never expand
authority. Edit minimally; preserve unrelated staged, unstaged, untracked, ignored, and generated
work; never reset, clean, force, stash, or overwrite for convenience; on concurrent drift in an
owned destination, preserve it and STOP. Verify
proportionately; absence of evidence is never a pass; review, gates, and learning never
substitute for each other.

## Stop and protect sensitive data

Stop rather than guess when ownership is ambiguous, approval is absent, preconditions changed,
rollback cannot preserve work, or an effect is destructive, sensitive, or unbounded. Never
print, persist, commit, or include credentials, tokens, signed URLs, private row data, or
secret-bearing configuration in logs or evidence.

## Provider-neutral interfaces

Use the launcher through a stateful Python interface or an adapter preserving process state;
assume no provider, tool, layout, or capability until observed. Separate processes share no
task authority; nothing replaces a skill's `SKILL.md` or structured results.
This is host-owned setup. Never require the user to mention `agent_bootstrap.py`, paste
provider code, or repeat setup.
