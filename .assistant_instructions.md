# Odibi Anchor operating contract

Use Odibi Anchor as a provider-neutral reliability and evidence layer. Own orientation,
context, implementation, and verification; users request outcomes, not action sequences.
The `.assistant` tree is a copyable skill distribution. Action help is under
`.assistant/references/odibi-anchor/`; other references hold engineering detail.

## ⛔ STOP — mandatory agent execution contract

**Odibi Anchor use is mandatory for every substantive repository, managed-project,
data, debugging, implementation, or multi-session task governed by these instructions.**
"Quick," "read-only," "just documentation," and "I already know the answer" are not
reasons to skip bootstrap, project verification, or task registration. Do not begin by
searching, editing, running tests, or querying data. First complete the applicable steps
below in order. If a required step blocks, follow its structured next action or STOP;
never rationalize a bypass.

### 1. Diagnose and bootstrap in the persistent Python process

Never assume the Python package is installed merely because guidance is present. On
Databricks/Genie, if the distribution is missing or is not exactly `0.3.5`, run:

```python
%pip install "odibi-anchor[databricks]==0.3.5"
dbutils.library.restartPython()
```

Resume in the same persistent Python process. Require
`importlib.metadata.version("odibi-anchor") == odibi_anchor.__version__ == "0.3.5"` and
`odibi_anchor.__file__` under its site-packages. Never substitute latest or a source checkout.
Load `setting-up-odibi-anchor` for missing, stale, unconfigured, or recovering installations.

On Databricks/Genie use the Python API, not a CLI subprocess. Never probe the durable Volume
through FUSE, map it to `ANCHOR_HOME`, or create replacement state after a failed launch:

```python
import os
import runpy
from odibi_anchor import prepare_portfolio_runtime

prepared = prepare_portfolio_runtime(
    config_path="<absolute-portfolio-path>",
    host_id="<host-id>",
    project_id="<project-id>",
)
os.environ.update(prepared["environment"])
bootstrap_path = prepared["next_operation"]["arguments"]["script"]
namespace = runpy.run_path(bootstrap_path)
anchor = namespace["anchor"]
ROOT = namespace["ROOT"]
MANIFEST = namespace["MANIFEST"]
orientation = namespace["ORIENTATION"]
bootstrap = namespace["BOOTSTRAP"]
assert bootstrap["success"] is True
assert orientation["kind"] == "orientation"
```

Preparation restores verified state locally and accesses `ANCHOR_DURABLE_ROOT` snapshots through
the Databricks Files API. Apply every returned environment value. Other hosts may use `anchor
portfolio prepare --config <path> --host <id> --project <id>`. Without a portfolio, explicit route
inputs are mandatory.

When guidance is absent or stale, run authorized `anchor setup-host <adapter> --target
<instruction-root>`. It upgrades unchanged managed files and refuses edits or collisions.

The instruction root contains this file and `.assistant/`. If deterministic resolution fails,
follow doctor's exact next operation. NEVER use `exec`, `eval`, manual `sys.path` reconstruction,
or a standalone subprocess; these can lose state or bypass safeguards.
Locating source or a failed init is not successful bootstrap.

Keep `namespace`, `anchor`, `orientation`, and `bootstrap` alive; after a process restart,
re-bootstrap and establish a fresh task. ALWAYS assign every `anchor()` result to a variable.
The process-bound `anchor` callable comes from the launcher namespace or `launch()` return value;
`from odibi_anchor import anchor` is not a supported import.
Issue exactly one Anchor call at a time and await its result. NEVER bundle,
parallelize, or concurrently execute Anchor calls; independent non-Anchor reads may run in parallel.
Follow the response's prepared `next_operation` and verified arguments. Call
`anchor("help", "action_name")` only when no prepared contract covers the intended action;
never guess parameters.

### 2. Verify the managed project before using repository or data context

Bootstrap restores the remembered managed project and returns status and audit orientation;
task-aware memory is deferred until acceptance. Inspect those structured results and then run:

```python
project_state = anchor("project", "status", output_format="dict")
```

- If the request names or clearly belongs to an existing managed project, the active
  project ID and target MUST match before substantive work.
- The immutable RouteBinding is routing authority. `workspace/.active_project` is only a
  legacy interactive preference and MUST NOT be used to infer, redirect, or validate a route.
- A request to work in one named existing project permits binding a fresh runtime to that
  exact project; it does NOT permit creation, retargeting, migration, deletion, or substitution.
- If the immutable binding names another project, do not call `project use` and continue in
  the same process. End that runtime, set the exact `ANCHOR_PROJECT_ID` and
  `ANCHOR_PROJECT_ROOT`, rerun the launcher, and rebind every result:

  ```python
  namespace = runpy.run_path(bootstrap_path)
  anchor = namespace["anchor"]
  ROOT = namespace["ROOT"]
  MANIFEST = namespace["MANIFEST"]
  orientation = namespace["ORIENTATION"]
  bootstrap = namespace["BOOTSTRAP"]
  project_state = anchor("project", "status", output_format="dict")
  ```

  Verify the bound ID and target, then create the fresh session/task for actual work.
  `anchor("project", "use", ...)` updates only legacy interactive selection state; it
  must not redirect an already-bound runtime.
- If an expected existing project is missing, ambiguous, inaccessible, or points at the
  wrong target, STOP. NEVER substitute another repository or silently work in the Anchor
  source checkout. If the user explicitly approved creation or retargeting instead,
  follow the separate write-capable setup lifecycle in the workflow reference, perform only
  that named mutation, re-bootstrap, and verify routing before actual work.
- Before planning or editing repository files, read and follow every applicable instruction
  file available from the selected target root through each target path. Recognize at least
  `.assistant_instructions.md`, `AGENTS.md`, and `CLAUDE.md` when present. Host-injected
  contents count as read; otherwise inspect the files directly. More-specific nested guidance
  governs its subtree without overriding system, user, task, managed-project, or trust-boundary
  authority. Do not scan unrelated subtrees. If required guidance is inaccessible, STOP.
- Read the selected project's `PROJECT.md` and the relevant current Problem, decision,
  work-item, and Spec records before planning. Do not start deferred work, silently broaden
  an accepted item, or fabricate retrospective work-item authority for changes already made.

Managed artifacts and implementation source are different authorities. Problems, Specs,
decisions, work items, durable session notebooks, and persisted managed evidence belong in
the active project's `artifact_root`; product code, product tests, and repository operations
belong in its exact `target_root`. Gates evaluate the active task and target and may persist
managed evidence through Odibi Anchor. Never copy product source into the artifact root
or scatter managed records through the target repository.

On Databricks, if serverless compute cannot perform an applicable investigation or test,
prefer a managed diagnostic notebook under the project's `artifact_root/notebooks/` so the
evidence remains resumable. Keep reusable product source in `target_root`. Attaching that
notebook to compute is an external effect: use only a specifically identified compatible
existing cluster when policy permits and owner approval already covers attachment. Never
select, start, create, resize, or install onto compute by inference. Otherwise return the
exact missing capability and stop condition.

### 3. Establish task authority before substantive work

Successful source bootstrap already executes one structured orientation containing
`status` and `audit_history`; do not repeat those calls merely as ceremony or issue a separate
pre-task memory query. The accepted task returns its bounded memory selections.
After project routing is correct, every substantive task MUST execute:

```python
session = anchor("new_session", name="bounded_task_name", inline=True, output_format="dict")
task = anchor(
    "task",
    "Describe the exact work to perform.",
    goal="State the intended outcome.",
    mode="implementation",  # choose the truthful mode
    acceptance_criteria=["State how completion will be verified."],
    output_format="dict",
)
```

After a host/process restart, first call `anchor("task_rebind")`. A matching open task
restores its exact window, baseline, and obligations. If unavailable, do not reconstruct
authority or use a new task to absorb existing changes. Dirty-task adoption is an exceptional,
authenticated recovery path; follow the prepared operation or workflow reference exactly.

For an intentional new continuation after the prior task is closed, omit `new_session` and
pass `continuation=True`; Anchor creates a fresh task window. This is replacement-task creation,
not durable rebinding.

For `work_item`, `scope` is one prose string; on rejection, inspect structured help.

Use a truthful mode; never choose write capability to bypass policy.
For routine substantive tasks, immediately after task acceptance and before source edits,
review only the bounded, active-project/trust-scoped `memory_context`. Acknowledge selected
memory IDs and provenance, or report that no memories were selected. Do not scan the full
store or treat a candidate as authority or verification. Dispose every selection and record
an evidence-backed evaluation for each application; runtime blocks learning closure until
every selection has a disposition and every application is evaluated. If retrieval is
unavailable, follow the fail-closed/degraded policy without inventing evidence.

### 4. Read and apply every materially matched skill

Use the routing matrix below and any required-skill result emitted by Odibi Anchor.
Before the skill-owned action, the agent MUST load the skill through the host or read the
exact `.assistant/skills/<name>/SKILL.md` file and follow it. File presence, a routing hint,
or prior familiarity is not skill loading. Only after loading a requested skill, register it
with `skill_result = anchor("skill_loaded", "<name>", output_format="dict")`. Do not claim a
skill was applied when it was not read.

`reference_guidance` is advisory, not a skill or gate. Load relevant entries before
technology decisions. Use `anchor("references", "search", "query")` and `load-section` for
offline depth; matches are not loaded content or runtime/host proof.

### 5. Complete the exact delivery lifecycle for file changes

For every file-changing task:

1. Inspect current source and preserve unrelated changes.
2. BEFORE editing any Python path, run
   `known_bad_result = anchor("known_bad", changed_files=["path.py"], output_format="dict")`.
3. Make only the task-authorized edit, then immediately register every path with
   `touch_result = anchor("touched", "path", output_format="dict")`.
4. After Python edits, run `preflight_result = anchor("preflight", output_format="dict")` and
   `test_result = anchor("test", output_format="dict")`. For other files, run the narrowest
   meaningful validation; never invent an irrelevant test merely for ceremony.
5. Review the complete final diff with
   `review_result = anchor("review", output_format="dict")` plus actual engineering judgment.
6. Run `gate_result = anchor("gate", output_format="dict")`. A task is not deliverable until
   the gate succeeds.
7. Capture observations when encountered. At closure, `assess` opens an obligation if
   needed, then closes it. Configured durable state checkpoints after successful authority writes:
   `learning_result = anchor("learning", "assess", outcome="nothing_reusable_learned", output_format="dict")`,
   or `capture` genuine observations and assess their returned IDs as
   `observations_recorded`. If gate is unavailable, assess first, then call
   `anchor("learning", "safe_stop", status="blocked", reason="...")`; it never passes gate.

When a reusable codebase observation is an exact callable behavior rather than prose, prefer
the machine-verifiable lane: the repository must own a tracked
`.odibi-anchor/memory-verifiers.json` entry that fixes the callable, inputs, and exact
assertions, and the learning summary must be
the canonical `PythonCallResultV1` produced by
`odibi_anchor.codebase._memory_verifier.canonical_python_call_result_claim`. Bind the
allowlisted source path as `file` evidence. A later independent task and source snapshot can
then verify and activate it mechanically; a second independent verification can confirm it.
Never encode preferences, policy, credentials, arbitrary expressions, or claims not completely
entailed by the exact JSON-pointer assertions in this lane.

Retain findings under the right authority: cross-project lessons in learning, project-specific
runs/deviations in managed evidence, and reproducible defects in a Problem or authorized Work
Item. Re-read every managed artifact after writing it; conversation is not durable fallback.

Do not edit after a successful gate. If follow-up changes are needed, first close that gate's
learning obligation, complete the authorized delivery boundary so the repository has a clean
baseline, then establish a fresh session/task and repeat the pre-edit checks, edit,
registration, validation, review, gate, and assessment. If a clean authorized baseline cannot
be established, STOP. For multiple coherent features, complete a checkpoint or full delivery
cycle at each boundary. Read-only tasks do not manufacture file, test, gate, or learning
obligations, but they still require bootstrap, correct project routing, and task authority
when they use project context.

### 6. Obey blockers; never self-authorize

Branch, revision, target, project, process, or worktree changes can invalidate authority.
When Odibi Anchor reports a block, drift, missing task, stale routing, required skill,
failed check, or active learning obligation, follow the stated recovery order. NEVER retry
the same failing action unchanged, edit around the guard, disable enforcement, fabricate
`obligations_paid`, treat skipped tests as passing, or claim completion from a summary.
STOP when recovery needs user approval, destructive action, unavailable credentials, an
unknown destination, or a choice between competing authorities.

### 7. Return a complete terminal contract

For every substantive project task, the final response MUST use this contract whether the
outcome is completed, blocked, or failed:

```text
Terminal return required:
- Status: completed, blocked, or failed
- Exact project/repository, branch, and revision
- Outcome and files/artifacts changed
- Checks actually executed and retained evidence
- Repository/host review, gate, and learning status where configured
- External/shared effects performed
- Commit, push, merge, deployment, and publication status
- Deviations, unavailable evidence, and residual uncertainty
- Decision or next authority required from me

Do not describe an unexecuted, skipped, unavailable, or failing check as passing.
```

Use `not performed`, `unavailable`, or `N/A` rather than omitting a material field. Re-read
persisted artifacts and external effects before claiming them. A stricter task-specific
return extends this contract. Casual conversation and simple factual answers are exempt.

## Route native skills by material intent

Before substantive work, select and apply through the host every native skill whose
material intent matches the request. Use this routing layer to activate the skill; its
`SKILL.md` remains the behavior authority.

| Native skill | Apply for this material intent | Do not apply for |
| --- | --- | --- |
| `auditing-memory-governance` | Audit or change memory seeds, lifecycle/schema migration, reconciliation, provenance/trust scope, diagnostics, cross-thread harvest, stale/duplicate/quarantined records, retrieval quality, or promotion candidates. | Ordinary implementation, routine bounded task-memory review, or generic learning capture. |
| `authoring-governed-memories` | Preserve a reusable fact, constraint, preference, failure pattern, or operating insight as a scoped, evidence-backed memory candidate and manage its lifecycle. | Raw notes, task authority, broad procedures, or full-store governance audits. |
| `building-memory-packs` | Bootstrap or maintain shared memory from an approved codebase, document set, decisions, or operational evidence with a complete source artifact and compact retrieval index. | Ad hoc single-memory capture, source documentation replacement, or unapproved cross-domain harvesting. |
| `code-comprehension` | Explain code behavior, locate implementation, trace flows or dependencies, and assess change impact. | Defect diagnosis, schema design, or implementation planning. |
| `cross-functional-pr` | Prepare an explicit PR, reviewer handoff, or cross-functional readiness evidence package. | Independent PR review, routine self-review, generic documentation, or work-item tracking. |
| `data-onboarding` | Ingest and profile a new or unfamiliar source and validate its quality and refresh contract. | Ongoing joins or writes, schema-only design, or source-to-target reconciliation proof. |
| `data-operations` | Transform, join, merge, write, or refresh operational data with mutation safety. | First ingestion, schema-only design, or reconciliation as the sole deliverable. |
| `data-reconciliation` | Prove source-to-target completeness and correctness using grain, keys, mappings, tolerances, and controls. | Generic profiling or onboarding, or ordinary ETL without a reconciliation outcome. |
| `debugging` | Reproduce, isolate, diagnose, fix, and verify non-incident defects, regressions, exceptions, or wrong results. | Live incident command or performance-only investigation. |
| `dependency-management` | Add, remove, pin, upgrade, evaluate, or troubleshoot dependencies and compatibility metadata. | General coding standards or tracing existing import flows. |
| `documentation` | Create or update user, operator, API, release, runbook, or architecture documentation as the deliverable. | Formal implementation Specs, work-item artifacts, or incidental code comments. |
| `incident-response` | Triage, contain, communicate, recover, and learn from an active outage or high-severity incident. | Ordinary defects or latency analysis without incident conditions. |
| `performance-investigation` | Measure, profile, attribute, and verify latency, throughput, memory, resource, or cost regressions. | Correctness debugging unless performance is the primary question. |
| `schema-design` | Design or evolve data or API schemas, grain, keys, constraints, compatibility, and migration implications. | Ingestion execution, dependency metadata, or reconciliation execution. |
| `setting-up-odibi-anchor` | Install, configure, diagnose, upgrade, or recover Anchor across local, Amp, Claude, ChatGPT, and Databricks hosts. | Ordinary managed work after a healthy exact runtime is already bound. |
| `work-item-management` | Create or refine managed Problems, decisions, work items, ownership, sequencing, handoffs, and stop conditions. | A requested implementation Spec body or generic planning without artifact or lifecycle intent. |
| `writing-specs` | Produce or revise an implementation-ready formal Spec for an explicit Spec or formal-contract request. | Generic planning, informal architecture discussion, or code changes without formal Spec intent. |
| `writing-tests` | Design or implement deterministic tests, fixtures, coverage, regression cases, or validation strategy. | Generic review or gating, or routine verification after edits. |

Independent PR review uses universal guidance outside the native skill registry. Fallback
routing is explicit: when the host provides `reviewing-pull-requests`, apply that host
skill; otherwise load and follow
`.assistant/references/reviewing/independent-pr-review.md`. Never route independent review
to `cross-functional-pr`, and keep the native distribution aligned with the canonical registry.

Compose multiple skills only when each owns a material outcome; never add a generic skill
merely because work requires planning or verification. Native host selection applies the
guidance. When a structured task response requires a direct skill,
`anchor("skill_loaded", "<name>")` returns its complete resolved content before registering it
in the current process. Registration proves delivery, not comprehension or correct
application; verify application from the plan, work, tests, and evidence.

## Reason from the outcome

Scale analysis to risk. Define outcome, scope, authority, evidence, risks, and stop conditions.
Test material uncertainty with evidence that can confirm and disconfirm it. Keep observation,
interpretation, and residual uncertainty distinct; process completion is not evidence.
Read-only work does not acquire manufactured edit, test, gate, or learning duties.

## Keep roots and authority separate

Distinguish product authority, repository root, workspace/project artifact roots, immutable
skill/resource source, writable Odibi Anchor home, target data systems, and host
deployment roots. Never infer authority or precedence from duplicate copies or from a tool's
capability. Verify active project, target, repository state, and applicable ancestor guidance.
Managed Problems, Specs, decisions, and evidence belong in their managed artifact root;
product source belongs only in the authorized target. Reconfirm destinations and approval at
write, publish, deploy, delete, compute, or external-service effect boundaries.
Use the versioned runtime artifact contract returned by `anchor("orient")` and
`anchor("task", ...)` to select managed records. It governs existing and new projects without
rewriting their records. Rebootstrap and orient after a Odibi Anchor upgrade before
substantive work.
For a referenced managed project, an existing external `target=` directory is expected: code
operations use it, while artifacts remain under `<ANCHOR_HOME>/workspace/projects/<project-id>`.
Only that managed destination existing or being a symlink is a project-creation collision.
Never rename, delete, convert, or manually scaffold an external target merely because it exists.

## Ask only at real boundaries

Ask only when intent is materially missing, a meaningful user choice exists, or an approval
boundary blocks safe progress. State bounded options and consequences. Otherwise verify facts
and proceed autonomously; do not interrupt for routine status or implementation details.

## Maintain one authoritative thread

Use one authoritative execution thread and explicit state. Do not duplicate hidden work.
For continuation, record completed evidence, current state, unresolved uncertainty, owned
paths, next action, and stop conditions; a handoff never silently expands authority.

## Edit minimally and preserve work

Inspect source and destination state before mutation. Make the smallest authorized edit,
preserve unrelated staged, unstaged, untracked, ignored, generated, or externally managed
work, and register every touched path accurately. Do not reset, clean, force, stash, discard,
overwrite, or broaden an allowlist for convenience. Keep source, artifacts, caches,
credentials, state, and target data in their proper roots. If concurrent drift affects an
owned destination, preserve it and stop rather than choosing a winner silently.

## Verify immediately and proportionately

After each edit, run the narrowest meaningful syntax, structure, or behavior check; run
broader checks at coherent phase boundaries. Review the complete final diff before delivery
and run only applicable authorized gates. Evidence must identify exact scope and provenance.
Anchor skill registration is bookkeeping, file presence is not discovery proof, and a summary
does not outrank source, repository, test, or external-system evidence. Report unavailable,
skipped, incomplete, and failing checks truthfully; absence of evidence is never a pass.

## Keep review, gates, and learning separate

Self-review is human/agent judgment over the complete change. Gates require their authorized
deterministic or attested evidence. Learning records capture bounded reusable observations;
they cannot fabricate or substitute for review or gate proof. Close with conclusions,
behavior/files changed, verification, limitations, and residuals rather than call transcripts.

## Stop and protect sensitive data

Stop rather than guess when ownership is ambiguous, required approval is absent,
preconditions changed, rollback cannot preserve work, or an effect is destructive, sensitive,
or unbounded. Never print, persist, commit, or include credentials, tokens, signed URLs,
private row data, or secret-bearing configuration in logs or evidence.

## Provider-neutral interfaces

Use the exact mandatory launcher contract above through a stateful Python interface or an
available transport adapter that preserves equivalent process state. Do not assume a
provider, generated tool name, filesystem layout, permission, or capability until observed;
separate processes do not share task authority. No custom registry, compatibility mapping,
or transport replaces each skill's own `SKILL.md` or the structured action results.

This is host-owned setup. Never require the user to mention `agent_bootstrap.py`, paste
provider code, or repeat setup commands. The invocation above is a troubleshooting fallback.
See `.assistant/references/odibi-anchor/workflow.md` for detailed signatures and
bounded provider examples.
